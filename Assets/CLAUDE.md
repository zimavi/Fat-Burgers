# CLAUDE.md — Sounding Rocket Mission Control Simulator

## 1. Project Overview

We are developing a **2D sounding rocket mission control and engineering simulation game** in **Unity using C#** for a **NASA hackathon with a 48-hour development window**.

The game combines spacecraft construction, simplified but physically meaningful rocket flight simulation, trajectory prediction, and interactive mission control.

The core inspiration is **Kerbal Space Program's trajectory planning and engineering gameplay**, combined with the interface and operational feeling of a real-world NASA mission control center.

However, this is **not a KSP clone**. The focus is on relatively short sounding rocket missions, scientific payload delivery, flight telemetry, and understanding how engineering decisions affect mission performance.

### Core Gameplay Loop

1. **Build:** Assemble a sounding rocket using a hierarchical component tree.
2. **Plan:** Calculate its predicted flight trajectory and identify important flight events.
3. **Launch:** Execute a launch and monitor the simulated vehicle in real time.
4. **Control:** Observe telemetry and execute available flight commands.
5. **Analyze:** Compare planned and actual flight performance, evaluate mission success, and improve the rocket.

The intended player experience is that of a mission engineer or flight controller, rather than a pilot flying a rocket manually.

## 2. Project Philosophy

The game should be:

- **Technically meaningful:** Simulated physical quantities should have real-world interpretations.
- **Accessible:** The player should not need aerospace engineering knowledge to understand the interface.
- **Visually informative:** Trajectories, telemetry, and flight events should communicate what is happening.
- **Deterministic where possible:** Repeating the same flight with identical vehicle configuration and inputs should produce the same result.
- **Modular:** Physics, vehicle construction, prediction, telemetry, and UI must be separated logically.
- **Achievable within 48 hours:** Prioritize a functioning, polished prototype over extensive features.

### Important Design Principle

**The simulation is the source of truth.**

The rocket's actual motion, predicted trajectory, event detection, and telemetry must use consistent physical models.

Avoid duplicating physics calculations across different components.

The game should not use arbitrary animations or scripted trajectories to simulate rocket flight.

## 3. Game Structure

The project consists of three main gameplay modes.

### 3.1 Vehicle Assembly

The player constructs a sounding rocket using a **hierarchical component tree**.

The tree represents the rocket's structural and functional composition.

Possible components include:

- Payload
- Payload fairing
- Avionics / guidance computer
- Fuel tank
- Rocket engine
- Structural components
- Stage separators
- Recovery systems
- Other mission-related equipment

Each component may define properties such as:

- Dry mass
- Fuel capacity
- Thrust
- Specific impulse
- Aerodynamic drag coefficient
- Cross-sectional area
- Thermal limits
- Structural limits

Not every component needs all these properties.

The vehicle's overall physical characteristics should be calculated from its components.

For the initial prototype, a constrained hierarchical assembly system is acceptable. A complex free-form editor is not required.

Prefer data-driven component definitions, using Unity ScriptableObjects where appropriate.

### 3.2 Mission Planning

Before launch, the player can examine the rocket's **predicted trajectory**.

This is conceptually similar to the trajectory preview in Kerbal Space Program.

The system should calculate the rocket's expected flight path using its current configuration and a defined flight program.

The prediction should include:

- Position over time
- Velocity over time
- Altitude over time
- Fuel consumption
- Atmospheric effects
- Expected flight events
- Estimated apoapsis
- Expected landing or impact location

The player should be able to inspect important events directly on the trajectory visualization.

The prediction should be generated by running the same physics simulation used during actual flight, but without affecting the real rocket state.

### 3.3 Mission Control / Live Flight

During flight, the player observes the rocket through a mission control interface.

The primary gameplay is **telemetry monitoring and mission management**, not direct arcade-style vehicle movement.

The UI should display relevant telemetry, potentially including:

- Mission elapsed time (MET)
- Altitude
- Vertical and horizontal velocity
- Total speed
- Acceleration
- Fuel remaining
- Thrust
- Atmospheric pressure
- Atmospheric density
- Dynamic pressure (Q)
- Aerodynamic heating indicator
- Predicted apoapsis
- Mission status

The player may execute available commands such as:

- Launch / ignition
- Engine cutoff (if supported by engine type)
- Stage separation
- Payload deployment
- Recovery system deployment

Only implement commands that are supported by the current vehicle and flight simulation.

## 4. Flight Physics

We want a **custom 2D rocket flight simulation** that is relatively simple computationally, but grounded in real physics.

The physics does not need to be aerospace-grade, but it should produce sensible behavior.

### 4.1 Basic State

The simulation should track at least:

- Position: `Vector2`
- Velocity: `Vector2`
- Vehicle orientation
- Angular state if rotation dynamics are implemented
- Current mass
- Fuel mass
- Engine state
- Flight phase
- Mission elapsed time

### 4.2 Forces

The initial model should include:

**Gravity**

Gravity should decrease with altitude using an inverse-square approximation:

`g(h) = g0 * (R / (R + h))²`

where:

- `g0` = surface gravitational acceleration
- `R` = planetary radius
- `h` = altitude above the surface

**Atmosphere**

An exponential atmosphere is sufficient for the prototype:

`rho(h) = rho0 * exp(-h / H)`

where:

- `rho0` = sea-level atmospheric density
- `H` = atmospheric scale height

A similar simplified approximation may be used for atmospheric pressure.

**Aerodynamic Drag**

`F_drag = 0.5 * rho * v² * Cd * A`

Drag acts opposite to velocity relative to the atmosphere.

**Thrust**

Thrust is generated by active engines in their configured direction.

Fuel consumption should affect the vehicle's mass over time.

Specific impulse may be used to calculate propellant consumption:

`mdot = T / (Isp * g0)`

Use the standard gravity constant for this equation.

**Dynamic Pressure**

`q = 0.5 * rho * v²`

Dynamic pressure is important because it allows the game to identify **Max Q**.

**Aerodynamic Heating**

Use a simplified heating indicator initially:

`heating ∝ sqrt(rho) * v³`

This is an approximation intended to represent the relative severity of aerodynamic heating, rather than an exact thermal engineering model.

Do not represent the heating indicator as an absolute temperature without a corresponding thermal model.

### 4.3 Numerical Integration

Use a deterministic fixed-timestep simulation.

Semi-implicit Euler or RK4 is acceptable.

Prefer simplicity, stability, and consistency over unnecessarily sophisticated methods.

Avoid depending on Unity Rigidbody2D for the primary rocket flight dynamics if doing so complicates deterministic trajectory prediction.

### 4.4 Coordinate System

Choose one clearly documented coordinate system and use it consistently throughout the simulation.

For the initial prototype, a flat 2D world with horizontal distance and vertical altitude is acceptable.

If a spherical-planet model is implemented, use planet-centered position vectors and radial gravity consistently.

Do not mix flat-world and spherical-world equations accidentally.

### 4.5 Units

Use SI units internally:

- Distance: meters
- Time: seconds
- Velocity: meters per second
- Acceleration: meters per second squared
- Mass: kilograms
- Force: newtons
- Pressure: pascals
- Temperature: kelvin, if a temperature model is implemented

UI may display converted units, such as kilometers or kilopascals.

**Do not use Unity world units interchangeably with physical meters without an explicit conversion.**

## 5. Trajectory System

The trajectory system is one of the most important features of the project.

It must support three related but distinct trajectories.

### 5.1 Preflight / Baked Trajectory

The preflight trajectory is calculated before launch.

It represents the expected flight based on:

- Rocket configuration
- Initial conditions
- Planned engine behavior
- Planned staging
- Planned guidance or orientation behavior
- Atmospheric conditions

The entire trajectory should be computed ahead of time.

It should be recalculated when relevant vehicle or flight-plan parameters change.

It must not be recalculated every rendered frame unless necessary.

### 5.2 Historical Trajectory

The historical trajectory is the path the rocket has actually traveled.

It should be recorded during flight.

Unlike predicted trajectories, it should not change retroactively.

### 5.3 Live Predicted Trajectory

During flight, the game should continuously update a prediction of the rocket's remaining trajectory.

The predictor should:

1. Copy the current rocket simulation state.
2. Use the same physics integration functions as the actual simulation.
3. Simulate the rocket into the future.
4. Assume a clearly defined future control program.
5. Record predicted positions and events.
6. Update the trajectory display.

Prediction does not need to run every rendered frame. It can update periodically, depending on performance.

Changes in throttle, orientation, staging, or other relevant control inputs should be reflected in subsequent predictions.

### 5.4 Trajectory Rendering

The trajectory display should visually distinguish:

- The original preflight trajectory
- The actual historical flight path
- The currently predicted future path

Use distinct line styles, colors, or opacity.

The rendering system must be separate from the underlying flight calculations.

The trajectory must be based on calculated simulation positions, not arbitrary Bézier curves.

Smooth visual interpolation is acceptable, as long as it does not misrepresent the simulated path.

## 6. Flight Event Markers

The trajectory should contain markers identifying important flight events.

These markers are a **major feature** of the game.

Events should be detected from simulated data, rather than positioned manually.

### Required or Desired Events

**Launch / Liftoff**

The vehicle begins ascending from its launch position.

**Max Q**

The point of maximum dynamic pressure during the relevant flight interval.

**Maximum Heating**

The point at which the aerodynamic heating indicator reaches its maximum.

**MECO — Main Engine Cutoff**

The main engine stops producing thrust.

**Stage Separation**

A rocket stage is detached from the vehicle.

**Space Boundary Crossing**

The vehicle crosses a defined altitude threshold, initially configurable to 100 km.

This threshold is a gameplay/reference convention, not a physical atmospheric discontinuity.

**Apoapsis / Apogee**

The highest point of the relevant trajectory.

For sounding rockets, apogee is generally the more natural term.

It occurs at the highest altitude of the flight, not necessarily at the highest speed.

**Payload Deployment**

A scientific payload is released from the rocket.

**Atmospheric Reentry**

The vehicle descends through a defined atmospheric or space-boundary threshold.

**Landing / Impact**

The rocket or payload reaches the surface.

### Event Data

Each event should ideally contain:

- Event type
- Simulation time
- Position
- Altitude
- Relevant telemetry
- Whether the event is historical, planned, or predicted

Events should be reusable by both the UI and mission evaluation systems.

### Event Detection

Use actual physics-based conditions.

Examples:

- Apogee: vertical/radial velocity changes from positive to zero or negative.
- Max Q: maximum dynamic pressure found along the simulated trajectory.
- Maximum heating: maximum value of the chosen heating metric.
- MECO: engine transitions from producing thrust to not producing thrust.
- Space boundary: altitude crosses the configured threshold.
- Impact: descending vehicle intersects the surface.

Use interpolation between simulation steps where necessary to improve event timing and positioning.

Do not confuse predicted events with confirmed flight events.

## 7. Mission Gameplay

The game should have meaningful objectives so that rocket construction and flight planning have a purpose.

Potential mission types include:

- Reach a specified altitude.
- Cross the 100 km space boundary.
- Deploy a payload within a specified altitude range.
- Keep maximum dynamic pressure below a specified limit.
- Keep heating below a specified limit.
- Reach a target downrange distance.
- Recover a payload safely.

Missions should be evaluated using measured simulated values.

The initial prototype only needs one fully functional mission, provided that it demonstrates the core gameplay loop.

### Mission Results

After flight, the game should provide a short evaluation including:

- Mission success or failure
- Maximum altitude reached
- Maximum dynamic pressure
- Maximum heating indicator
- Payload deployment status
- Landing / impact location
- Differences between predicted and actual performance

The player should be able to return to assembly and improve the vehicle.

## 8. UI / Visual Design

The game's visual direction is **NASA-inspired mission control**, with functional engineering interfaces.

It should feel like a serious but understandable flight simulation.

Suggested UI elements:

- Flight trajectory/map display
- Rocket configuration tree
- Telemetry panels
- Mission elapsed time
- Flight event timeline
- Mission objectives
- Launch controls
- Flight status indicators
- Mission results screen

Prioritize readable information over decorative complexity.

Important values and warnings should be easy to identify.

For example, high dynamic pressure should be noticeable before it causes a mission problem.

A clean 2D interface is preferable to elaborate graphics that consume development time.

## 9. Software Architecture

Use separation of responsibilities.

Suggested conceptual modules:

**RocketComponent**

Represents a vehicle part and its physical/functional characteristics.

**RocketConfiguration**

Represents assembled vehicle structure and aggregate properties.

**RocketState**

Contains the mutable simulation state of a vehicle.

**FlightDynamics**

Calculates gravity, drag, thrust, mass changes, and other physical effects.

**FlightSimulator**

Advances the rocket state using a deterministic timestep.

**FlightProgram**

Defines planned engine operations, orientation commands, and deployment/staging events.

**TrajectoryPredictor**

Runs the flight simulator on a copied state to produce predicted future states.

**TrajectoryData**

Stores sampled trajectory points and associated events.

**FlightEventDetector**

Identifies significant events from simulation states and transitions.

**TelemetryProvider**

Extracts physical quantities for display in the UI.

**TrajectoryRenderer**

Visualizes trajectory data without controlling the simulation.

**MissionController**

Manages launch, flight, and mission progression.

**MissionEvaluator**

Checks mission requirements and generates results.

These are conceptual responsibilities, not a requirement to create exactly one C# class per item.

Favor a small, maintainable implementation over excessive abstraction.

### Critical Architectural Requirement

**Do not implement separate physics models for flight and prediction.**

The actual flight simulator and trajectory predictor should share the same simulation step.

Prediction should operate on independent state copies and must never mutate the active flight state.

## 10. Development Constraints

This project is being developed during a **48-hour hackathon**.

Time and implementation complexity are critical constraints.

### Highest Priority — Minimum Viable Game

1. Functional vehicle assembly/configuration.
2. Working 2D rocket physics.
3. Preflight trajectory simulation.
4. Live flight simulation.
5. Live trajectory prediction.
6. Trajectory event markers.
7. Telemetry visualization.
8. At least one complete mission objective.
9. Mission success/failure evaluation.

### Secondary Priority

- Multiple rocket stages
- Interactive payload deployment
- Recovery systems
- Thermal or structural damage
- Additional mission types
- Expanded component selection
- More advanced telemetry

### Low Priority / Future Features

- Full orbital mechanics
- Detailed six-degree-of-freedom physics
- High-fidelity atmospheric modeling
- Complex aerodynamic stability
- Advanced guidance computers
- Detailed part-to-part structural simulation
- Complex rocket editor interactions
- Multiplayer
- Elaborate cinematic effects

Do not implement low-priority systems before the core gameplay is working.

## 11. Guidelines for Claude

When helping with this project, follow these rules:

1. **Preserve the project vision.** This is a mission control and engineering simulation, not an arcade rocket game.
2. **Respect the 48-hour constraint.** Propose solutions that can realistically be developed and tested during a hackathon.
3. **Prefer working implementations.** Avoid unnecessary architectural complexity.
4. **Maintain physical consistency.** Use one authoritative simulation model.
5. **Keep rendering separate from simulation.** Visual presentation must not determine physical behavior.
6. **Use SI units internally.** Clearly document any conversions.
7. **Make systems reusable.** In particular, actual flight, preflight prediction, and live prediction should share code.
8. **Keep event detection extensible.** Adding new flight event types should not require rewriting the simulation.
9. **Avoid assumptions about existing project structure.** Inspect the relevant Unity files before making changes.
10. **Do not introduce external packages unnecessarily.** Prefer built-in Unity functionality and standard C#.
11. **Avoid replacing existing working systems without a clear reason.**
12. **Identify dependencies before implementing features.**
13. **Explain important physics simplifications and their limitations.**
14. **Consider performance**, especially when predicting trajectories repeatedly.
15. **Prioritize testability.** Physics and trajectory calculations should be testable independently from Unity scenes and UI.
16. **Do not invent completed functionality.** Clearly distinguish existing code from proposed features.
17. **Keep new code compatible with the Unity and C# versions used by the project.**

When asked to implement a feature:

- First inspect the relevant existing code.
- Identify which systems need modification.
- Choose the simplest architecture that meets the requirements.
- Implement the functionality without introducing unrelated changes.
- Account for edge cases and invalid states.
- Explain any assumptions, limitations, and required Unity scene/prefab setup.
- Do not add speculative features unless explicitly requested.

## 12. Definition of Success

The hackathon prototype is successful if a player can:

1. Assemble a simple sounding rocket.
2. See its physically simulated predicted trajectory.
3. Examine predicted flight events such as Max Q, MECO, and apogee.
4. Launch the rocket.
5. Monitor its flight using telemetry.
6. Compare its actual path to its original prediction.
7. Observe live updates of its projected future trajectory.
8. Complete or fail a meaningful scientific mission.
9. Understand why the mission succeeded or failed.

**The most important technical achievement is a unified flight simulation capable of generating both real-time motion and forward trajectory predictions, with automatically calculated event markers.**

**The most important gameplay achievement is making rocket engineering decisions visibly affect mission outcomes.**
